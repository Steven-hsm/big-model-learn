### Day 1: 模型量化

#### 3.1.1 量化原理

```
量化：降低模型参数的数值精度，减少存储和计算开销

FP32 (32-bit浮点数) → INT8 (8-bit整数) → INT4 (4-bit整数)

存储节省：
  FP32: 7B × 4 bytes = 28 GB
  FP16: 7B × 2 bytes = 14 GB
  INT8: 7B × 1 byte  = 7 GB
  INT4: 7B × 0.5 byte = 3.5 GB

精度影响（通常 INT4 精度损失 < 1%）：
  FP16 → INT8: 几乎无损
  FP16 → INT4: 轻微损失，可通过GPTQ/AWQ补偿
```

#### 3.1.2 量化方法对比

**PTQ (Post-Training Quantization) - 训练后量化**

```
直接量化，不需要重新训练
简单快速，但可能有精度损失
适合：快速部署，对精度要求不极端的场景
```

**QAT (Quantization-Aware Training) - 量化感知训练**

```
训练时模拟量化效果，让模型适应低精度
精度更好，但需要训练资源和数据
适合：对精度要求高的场景
```

**GPTQ (GPT Quantization)**

```
基于Hessian信息的逐层量化
原理：利用二阶信息（Hessian矩阵）找到最优量化参数
  - 逐层处理，每层独立量化
  - 利用Hessian矩阵的近似逆，最小化量化误差
  - 对每层的权重分组量化（group_size=128）

特点：
  - 需要"校准数据集"（几百条样本）来确定量化参数
  - 量化后模型保持较高精度
  - GPU推理速度快
  - 适合：GPU部署场景
```

```python
# GPTQ量化
from transformers import AutoTokenizer, AutoModelForCausalLM, GPTQConfig

tokenizer = AutoTokenizer.from_pretrained("model_name")

# 准备校准数据
calibration_data = ["示例文本1", "示例文本2", ...]

gptq_config = GPTQConfig(
    bits=4,                    # 4-bit量化
    dataset=calibration_data,  # 校准数据集
    group_size=128,            # 分组大小
    desc_act=True,             # 按重要性排序量化
)

model = AutoModelForForCausalLM.from_pretrained(
    "model_name",
    quantization_config=gptq_config,
    device_map="auto",
)
```

**AWQ (Activation-aware Weight Quantization)**

```
基于激活感知的权重量化
原理：不是所有权重同等重要，AWQ识别"重要权重"并保护它们
  - 通过分析激活值（Activation）来判断权重的重要性
  - 对重要权重使用更高精度
  - 对非重要权重进行激进量化

与GPTQ的区别：
  GPTQ: 基于Hessian（损失函数的二阶导数）
  AWQ:  基于激活值（实际使用中的信号强度）
  AWQ通常更快、更稳定
```

```python
# AWQ量化
from awq import AutoAWQForCausalLM

model = AutoAWQForCausalLM.from_pretrained("model_name")
tokenizer = AutoTokenizer.from_pretrained("model_name")

quant_config = {
    "zero_point": True,
    "q_group_size": 128,
    "w_bit": 4,                # 4-bit量化
}

model.quantize(tokenizer, quant_config=quant_config)
model.save_quantized("./model-awq-4bit")
```

**GGUF (llama.cpp格式)**

```
专为CPU推理优化的格式
由llama.cpp项目开发
支持多种量化级别：Q4_0, Q4_K_M, Q5_0, Q5_K_M, Q8_0等

特点：
  - CPU友好（也支持GPU加速）
  - 内存映射(mmap)加载，启动快
  - 适合消费级硬件
  - Ollama底层使用GGUF格式
```

```bash
# 量化
```

### Day 2: 推理引擎vLLM

#### 3.2.1 vLLM核心创新

**PagedAttention**

```
问题：传统推理中，KV Cache预分配固定大小的连续显存
  → 显存碎片化严重，浪费50-80%的显存

解决：PagedAttention借鉴操作系统的虚拟内存分页机制
  - KV Cache分成固定大小的"页"(block)
  - 不需要连续的显存空间
  - 动态分配和回收页
  - 显存利用率接近100%

类比：
  传统: 每个请求预分配一块大内存（类似C的malloc）
  PagedAttention: 按需分页（类似操作系统的虚拟内存）
```

**Continuous Batching**

```
传统Static Batching：
  等凑够batch_size个请求 → 一起处理 → 等最慢的完成 → 返回
  → 短请求被长请求拖慢

Continuous Batching：
  请求级别的动态批处理
  → 新请求随时加入batch
  → 完成的请求立即返回，空出位置给新请求
  → 吞吐量提升2-4倍
```

#### 3.3.1 PyTorch → ONNX

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "gpt2"  # 示例用小模型
model = AutoModelForCausalLM.from_pretrained(model_name)
tokenizer = AutoTokenizer.from_pretrained(model_name)

dummy_input = tokenizer("Hello world", return_tensors="pt")

# 导出ONNX
torch.onnx.export(
    model,
    (dummy_input["input_ids"], dummy_input["attention_mask"]),
    "model.onnx",
    input_names=["input_ids", "attention_mask"],
    output_names=["logits"],
    dynamic_axes={
        "input_ids": {0: "batch_size", 1: "sequence_length"},
        "attention_mask": {0: "batch_size", 1: "sequence_length"},
        "logits": {0: "batch_size", 1: "sequence_length"},
    },
    opset_version=14,
)
print("ONNX模型已导出: model.onnx")
```

#### 3.3.2 ONNX → TensorRT

```bash
# 使用trtexec工具转换
trtexec --onnx=model.onnx \
        --saveEngine=model.engine \
        --fp16 \                        # 使用FP16精度
        --maxBatch=8 \                  # 最大batch size
        --minShapes=input_ids:1x64 \
        --optShapes=input_ids:4x128 \
        --maxShapes=input_ids:8x256

# 使用TensorRT Python API
import tensorrt as trt

logger = trt.Logger(trt.Logger.WARNING)
builder = trt.Builder(logger)
network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
parser = trt.OnnxParser(network, logger)

with open("model.onnx", "rb") as f:
    parser.parse(f.read())

config = builder.create_builder_config()
config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 4 << 30)  # 4GB
config.set_flag(trt.BuilderFlag.FP16)

engine = builder.build_serialized_network(network, config)
with open("model.engine", "wb") as f:
    f.write(engine)
```

### Day 4: 服务化部署

#### 3.4.1 FastAPI封装推理接口

```python
from fastapi import FastAPI, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from typing import List, Optional
import asyncio
import time

app = FastAPI(title="AI模型推理服务", version="1.0.0")

# 请求/响应模型
class GenerateRequest(BaseModel):
    prompt: str
    max_tokens: int = 256
    temperature: float = 0.7
    top_p: float = 0.9
    stream: bool = False

class GenerateResponse(BaseModel):
    text: str
    tokens_used: int
    latency_ms: float

class ChatRequest(BaseModel):
    messages: List[dict]
    max_tokens: int = 256
    temperature: float = 0.7
    stream: bool = False

# 全局模型（启动时加载）
model = None
tokenizer = None

@app.on_event("startup")
async def load_model():
    """启动时加载模型"""
    global model, tokenizer
    from transformers import AutoModelForCausalLM, AutoTokenizer
    import torch

    model_name = "./merged_model"  # 微调后的模型
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModelForCausalLM.from_pretrained(
        model_name,
        device_map="auto",
        torch_dtype=torch.bfloat16,
    )
    print(f"模型已加载: {model_name}")

@app.post("/generate", response_model=GenerateResponse)
async def generate(request: GenerateRequest):
    """文本生成接口"""
    start_time = time.time()

    try:
        import torch
        inputs = tokenizer(request.prompt, return_tensors="pt").to(model.device)
        with torch.no_grad():
            outputs = model.generate(
                **inputs,
                max_new_tokens=request.max_tokens,
                temperature=request.temperature,
                top_p=request.top_p,
                do_sample=True,
            )
        text = tokenizer.decode(outputs[0], skip_special_tokens=True)
        # 去掉输入prompt
        generated_text = text[len(request.prompt):]
        latency = (time.time() - start_time) * 1000

        return GenerateResponse(
            text=generated_text,
            tokens_used=len(outputs[0]) - len(inputs["input_ids"][0]),
            latency_ms=latency,
        )
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

@app.post("/generate/stream")
async def generate_stream(request: GenerateRequest):
    """流式生成接口（SSE）"""
    async def stream_generator():
        from transformers import TextIteratorStreamer
        import threading

        streamer = TextIteratorStreamer(tokenizer, skip_special_tokens=True)
        inputs = tokenizer(request.prompt, return_tensors="pt").to(model.device)

        # 在线程中生成
        generation_kwargs = {
            **inputs,
            "max_new_tokens": request.max_tokens,
            "temperature": request.temperature,
            "streamer": streamer,
            "do_sample": True,
        }
        thread = threading.Thread(target=model.generate, kwargs=generation_kwargs)
        thread.start()

        for text in streamer:
            yield f"data: {text}\n\n"

        thread.join()
        yield "data: [DONE]\n\n"

    return StreamingResponse(
        stream_generator(),
        media_type="text/event-stream",
    )

@app.get("/health")
async def health_check():
    """健康检查"""
    return {"status": "healthy", "model_loaded": model is not None}

@app.get("/ready")
async def readiness_check():
    """就绪检查"""
    if model is None:
        raise HTTPException(status_code=503, detail="Model not loaded")
    return {"status": "ready"}

@app.get("/metrics")
async def metrics():
    """基础指标"""
    import psutil
    return {
        "cpu_percent": psutil.cpu_percent(),
        "memory_percent": psutil.virtual_memory().percent,
        "gpu_available": torch.cuda.is_available(),
        "gpu_memory_used": torch.cuda.memory_allocated() if torch.cuda.is_available() else 0,
    }
```

### Day 5: 性能优化

#### 3.5.1 KV Cache原理

```
KV Cache：缓存已计算的Key/Value矩阵，避免重复计算

不使用KV Cache：
  Step1: 计算 K1,V1,A1    → 生成 token1
  Step2: 计算 K1,K2,V1,V2,A2  → 生成 token2（重新计算K1,V1）
  Step3: 计算 K1,K2,K3,V1,V2,V3,A3 → 生成 token3（重新计算K1,V1,K2,V2）

使用KV Cache：
  Step1: 计算 K1,V1,A1    → 生成 token1  → 缓存K1,V1
  Step2: 计算 K2,V2,A2    → 生成 token2  → 缓存K2,V2（不重新计算K1,V1）
  Step3: 计算 K3,V3,A3    → 生成 token3  → 缓存K3,V3

生成N个token的计算量：
  无Cache: O(N²)     → 每步重新计算所有之前的KV
  有Cache: O(N)      → 每步只计算新的KV

KV Cache显存占用：
  每层: 2 × batch_size × seq_len × hidden_dim × sizeof(float16)
  7B模型(4096 hidden, 32层): 2 × 1 × 2048 × 4096 × 2 × 32 ≈ 1GB
```

#### 3.5.2 批量推理

```python
# 批量推理：一次处理多个请求，提高GPU利用率
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model = AutoModelForCausalLM.from_pretrained("./model", device_map="auto")
tokenizer = AutoTokenizer.from_pretrained("./model")

# 批量推理
def batch_generate(prompts, max_tokens=128, batch_size=4):
    results = []
    for i in range(0, len(prompts), batch_size):
        batch = prompts[i:i + batch_size]
        inputs = tokenizer(batch, return_tensors="pt", padding=True, truncation=True).to(model.device)

        with torch.no_grad():
            outputs = model.generate(
                **inputs,
                max_new_tokens=max_tokens,
                do_sample=True,
                temperature=0.7,
            )

        for j, output in enumerate(outputs):
            text = tokenizer.decode(output, skip_special_tokens=True)
            results.append(text)
    return results

# 使用
prompts = ["问题1", "问题2", "问题3", "问题4", "问题5"]
results = batch_generate(prompts, batch_size=4)
```

```python
# gateway/app.py
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from typing import List, Optional
import httpx
import time
import asyncio
import redis

app = FastAPI(title="AI模型服务网关")

# 配置
VLLM_URL = "http://vllm-server:8000"
redis_client = redis.Redis(host="redis", port=6379, decode_responses=True)

class ChatRequest(BaseModel):
    messages: List[dict]
    max_tokens: int = 256
    temperature: float = 0.7
    stream: bool = False

@app.post("/v1/chat/completions")
async def chat_completions(request: ChatRequest):
    """代理到vLLM的聊天接口"""
    start_time = time.time()

    # 检查缓存
    cache_key = _make_cache_key(request)
    cached = redis_client.get(cache_key)
    if cached and not request.stream:
        return {"cached": True, **eval(cached)}

    # 转发到vLLM
    async with httpx.AsyncClient(timeout=60.0) as client:
        if request.stream:
            return StreamingResponse(
                _stream_proxy(client, request),
                media_type="text/event-stream",
            )
        else:
            response = await client.post(
                f"{VLLM_URL}/v1/chat/completions",
                json=request.dict(),
            )
            result = response.json()

    # 缓存结果（非流式）
    if not request.stream:
        redis_client.setex(cache_key, 3600, str(result))

    latency = (time.time() - start_time) * 1000
    result["gateway_latency_ms"] = latency
    return result

async def _stream_proxy(client, request):
    """流式代理"""
    async with client.stream(
        "POST",
        f"{VLLM_URL}/v1/chat/completions",
        json=request.dict(),
    ) as response:
        async for chunk in response.aiter_text():
            yield chunk

def _make_cache_key(request):
    """生成缓存key"""
    import hashlib, json
    data = json.dumps(request.dict(), sort_keys=True)
    return f"chat:{hashlib.md5(data.encode()).hexdigest()}"

@app.get("/health")
async def health():
    return {"status": "healthy", "vllm_url": VLLM_URL}
```

## 六、自测题

### 题目

1. **GPTQ和AWQ的区别？**

<details>
<summary>参考答案</summary>

GPTQ和AWQ都是4-bit训练后量化方法，但原理不同：GPTQ基于Hessian矩阵（损失函数的二阶信息），逐层最小化量化误差，需要校准数据集和Hessian计算，量化过程较慢但效果好。AWQ基于激活感知（Activation-aware），通过分析激活值判断权重的重要性，保护重要权重不被过度量化，不需要Hessian计算，量化速度更快。实践中AWQ更简单稳定，GPTQ在某些模型上精度略高。两者精度损失都小于1%。
</details>

2. **vLLM的PagedAttention解决了什么问题？**

<details>
<summary>参考答案</summary>

PagedAttention解决了KV Cache的显存管理问题。传统推理中，每个请求的KV Cache需要预分配一块连续的显存，导致：(1) 显存碎片化严重——不同请求的KV Cache长度不同，频繁分配释放产生碎片；(2) 显存浪费50-80%——预分配按最大长度，实际使用远小于预分配。PagedAttention借鉴操作系统虚拟内存分页机制，将KV Cache分成固定大小的"页"，按需动态分配，不需要连续空间，显存利用率接近100%，使得同样显存能服务更多并发请求。
</details>

3. **为什么需要ONNX和TensorRT？**

<details>
<summary>参考答案</summary>

ONNX（Open Neural Network Exchange）解决框架互操作问题：不同训练框架（PyTorch/TensorFlow/JAX）训练的模型可以统一转为ONNX格式，在不同推理引擎上运行。TensorRT是NVIDIA的推理优化引擎，对ONNX模型做深度优化：(1) 层融合（Layer Fusion）——合并多个计算层减少显存访问；(2) 精度校准——自动选择最优的计算精度；(3) 内核自动调优——针对特定GPU选择最快的计算内核；(4) 动态显存管理——优化显存使用。TensorRT通常能将推理速度提升2-5倍，但仅限NVIDIA GPU。
</details>

4. **Docker部署AI服务的注意事项？**

<details>
<summary>参考答案</summary>

(1) GPU支持：基础镜像要选nvidia/cuda，docker-compose中需要配置GPU资源分配（deploy.resources.reservations.devices）；(2) 显存管理：通过gpu_memory_utilization参数控制vLLM的显存使用率，不要让单个服务占满GPU；(3) 健康检查：模型加载需要时间，start-period要设长（如120秒），避免健康检查误判；(4) 模型缓存：通过volume挂载HuggingFace缓存目录，避免每次重启重新下载模型；(5) 超时设置：推理请求可能较慢，HTTP超时要设置足够长（如60秒）；(6) 内存限制：设置合理的内存限制，防止OOM影响其他服务。
</details>

5. **Spring AI/LangChain4j适合什么场景？**

<details>
<summary>参考答案</summary>

Spring AI和LangChain4j适合企业级AI应用开发场景，发挥Java生态的优势：(1) 已有Spring Boot项目需要集成AI能力——直接在现有项目中添加AI功能，不需要另起Python服务；(2) 企业级需求——权限管理(Spring Security)、事务处理、消息队列(Kafka)、API网关等；(3) 混合架构——Java做业务逻辑层和API层，Python做推理层，Java通过REST/gRPC调用Python推理服务；(4) RAG应用——LangChain4j支持向量存储和检索，可以构建Java版RAG应用。不适合的场景：模型训练、复杂的Agent系统（Python生态更丰富）。
</details>
