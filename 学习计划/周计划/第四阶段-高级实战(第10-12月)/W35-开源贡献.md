#### 选择Issue的标准

```
筛选Good First Issue的标准：

✅ 推荐选择：
  1. 标签包含 "good first issue" / "help wanted" / "documentation"
  2. 评论少于5条的Issue（竞争少）
  3. 近期有维护者回复的Issue（项目活跃）
  4. 文档改进或测试补充类Issue（难度低，容易合并）
  5. 你能理解问题描述的Issue

❌ 避免选择：
  1. 已有人认领但长期未提交PR的Issue
  2. 超过6个月无人回复的Issue
  3. 标记为 "wontfix" / "out of scope" 的Issue
  4. 涉及核心架构改动的大Issue
  5. 争议较大的Issue（评论中有多人争论）

策略：选3-5个候选Issue，按难度排序，先做最简单的
```

#### 安装开发依赖

```bash

pip install -e ".[testing]"  # 只安装测试依赖
```

#### 运行测试

```bash
# 运行全部测试（可能很慢）
pytest tests/

# 只运行特定模块的测试
pytest tests/test_tokenization.py

# 运行单个测试
pytest tests/test_tokenization.py::TestTokenizer::test_encode

# 查看测试覆盖率
pytest tests/ --cov=src --cov-report=term-missing

# 确保你修改的模块相关测试全部通过
pytest tests/test_your_module.py -v
```

#### 配置pre-commit hooks

```bash
# 安装pre-commit
pip install pre-commit

# 安装项目的hooks
pre-commit install

# 手动运行所有hooks（提交前检查）
pre-commit run --all-files

# 常见的pre-commit hooks：
# - black: 代码格式化
# - isort: import排序
# - flake8: 代码规范检查
# - mypy: 类型检查
# - trailing-whitespace: 删除行末空白
# - end-of-file-fixer: 文件末尾换行
```

```
pre-commit的作用：
1. 自动格式化代码（black/isort）
2. 检查代码规范（flake8）
3. 发现潜在问题（mypy）
4. 统一团队代码风格
5. 防止低级错误进入代码库

常见pre-commit触发时机：
- git commit时自动触发
- 也可以手动运行：pre-commit run --all-files
```

```python
# 示例：为HuggingFace Transformers的Tokenizer添加文档字符串

# 修改前：
def encode(self, text, add_special_tokens=True):
    tokens = self._tokenize(text)
    if add_special_tokens:
        tokens = [self.cls_token_id] + tokens + [self.sep_token_id]
    return tokens

# 修改后（添加完整的docstring）：
def encode(self, text: str, add_special_tokens: bool = True) -> list[int]:
    """将文本编码为token ID列表。

    Args:
        text (`str`):
            需要编码的文本。
        add_special_tokens (`bool`, *optional*, 默认为 `True`):
            是否添加特殊token（如 [CLS], [SEP]）。

    Returns:
        `list[int]`: token ID列表。

    Example:
        >>> from transformers import AutoTokenizer
        >>> tokenizer = AutoTokenizer.from_pretrained("bert-base-uncased")
        >>> tokenizer.encode("Hello, world!")
        [101, 7592, 1010, 2088, 999, 102]

    Note:
        此方法返回token ID列表。如果需要同时获取token字符串，
        请使用 `tokenize()` 方法。
    """
    tokens = self._tokenize(text)
    if add_special_tokens:
        tokens = [self.cls_token_id] + tokens + [self.sep_token_id]
    return tokens
```

#### 代码贡献示例：Bug修复

```python
# 示例：修复一个文档解析器处理空文件的Bug

# 修改前（有Bug）：
def parse_file(file_path):
    with open(file_path) as f:
        content = f.read()
    # 没有处理空文件的情况
    lines = content.split('\n')
    return {'title': lines[0], 'body': '\n'.join(lines[1:])}

# 修改后（修复Bug + 添加测试）：
def parse_file(file_path: str) -> dict:
    """解析文件，返回标题和正文。

    Raises:
        ValueError: 当文件为空时抛出。
        FileNotFoundError: 当文件不存在时抛出。
    """
    with open(file_path, encoding='utf-8') as f:
        content = f.read()

    if not content.strip():
        raise ValueError(f"文件为空: {file_path}")

    lines = content.split('\n')
    return {
        'title': lines[0],
        'body': '\n'.join(lines[1:]),
    }

# 对应的测试
def test_parse_file_empty():
    """测试空文件处理"""
    import tempfile
    with tempfile.NamedTemporaryFile(mode='w', suffix='.txt', delete=False) as f:
        f.write("")  # 空文件
        temp_path = f.name

    try:
        with pytest.raises(ValueError, match="文件为空"):
            parse_file(temp_path)
    finally:
        import os
        os.unlink(temp_path)
```

#### 提交PR流程

```bash
# 1. 确保代码是最新的
git fetch upstream
git rebase upstream/main

# 2. 推送到你的Fork
git push origin fix/issue-12345-add-docstring

# 3. 使用gh CLI创建PR
gh pr create \
  --repo huggingface/transformers \
  --title "fix: add docstring to encode() method" \
  --body "$(cat <<'EOF'
## Description
Fixes #12345

Added comprehensive docstring to the `encode()` method including:
- Parameter descriptions
- Return type documentation
- Usage example
- Edge case notes

## Testing
- [x] All existing tests pass
- [x] Pre-commit hooks pass
EOF
)"

# 4. 或者在GitHub网页上创建PR
# 进入你Fork的仓库页面，GitHub会提示"Create Pull Request"
```

#### Code Review回应

```
收到Review后的应对策略：

1. 保持礼貌和专业
   ✅ "好的建议，我已经修改了"
   ✅ "感谢指出，我来解释一下这个设计选择"
   ❌ "你不懂这个功能"
   ❌ "这不是bug是feature"

2. 逐条回复每条评论
   - 同意的建议：直接修改并回复"Done"
   - 不同意的建议：礼貌解释你的理由
   - 不确定的建议：请求更多上下文

3. 及时响应
   - 尽量在24小时内回复Review
   - 推送修改后主动通知Reviewers

4. 根据反馈修改代码
   # 修改代码后
   git add .
   git commit -m "address review feedback: add type hints"
   git push origin fix/issue-12345-add-docstring

   # 如果需要rebase（保持提交历史整洁）
   git rebase -i HEAD~3  # 整理最近3个commit
   git push origin fix/issue-12345-add-docstring --force-with-lease
```

### 参考答案

<details>
<summary>点击展开答案</summary>

1. **判断标准**：(1) Issue带有 "good first issue" 或 "help wanted" 标签。(2) Issue描述清晰，包含复现步骤和期望行为。(3) 评论数少于5条，竞争不激烈。(4) 近期有维护者回复，项目活跃。(5) 属于文档改进或测试补充类型（难度较低）。(6) 你能理解问题并与你的技术栈相关。

2. **PR被接受的条件**：(1) **代码质量**：符合项目代码规范，有文档字符串和类型注解。(2) **测试覆盖**：为新代码编写了测试，所有现有测试通过。(3) **PR描述清晰**：说明做了什么、为什么做、如何测试。(4) **一个PR一件事**：不要混合多个不相关的变更。(5) **基于最新代码**：rebase到最新的main分支。(6) **Review通过**：至少一个维护者Approve。(7) **CI通过**：所有自动化检查通过。

3. **pre-commit作用**：在git commit时自动运行代码检查，确保提交的代码符合项目规范。**常见hooks**：(1) **black** - 自动格式化Python代码。(2) **isort** - 自动排序import语句。(3) **flake8** - 检查代码规范（未使用变量、过长行等）。(4) **mypy** - 类��检查。(5) **trailing-whitespace** - 删除行末空白。(6) **end-of-file-fixer** - 确保文件末尾有换行符。(7) **check-yaml** - 验证YAML语法。(8) **check-merge-conflict** - 检查合并冲突标记。

4. **Code Review反馈类型**：(1) **Bug/错误** - 代码逻辑有误。应对：感谢指出，立即修复。(2) **代码风格** - 命名不规范、格式问题。应对：按建议修改。(3) **设计建议** - 更好的实现方式。应对：评估建议，合理则采纳，否则解释理由。(4) **性能问题** - 可以优化的热点。应对：评估是否真的需要优化，必要时添加性能测试。(5) **遗漏** - 缺少边界处理、错误处理。应对：补充处理逻辑。(6) **nit** - 小问题（拼写错误等）。应对：快速修复。核心原则：保持礼貌，逐条回复，及时响应。

5. **评估维度**：(1) **项目活跃度** - 近期commit频率、Issue响应速度、PR合并速度。(2) **社区友好度** - 是否有Contributing指南、Code of Conduct、Good First Issue标签。(3) **技术相关性** - 项目是否与你的技术栈和兴趣方向一致。(4) **Star数和用户基数** - Star多通常意味着项目质量高、影响大。(5) **维护者态度** - Review是否及时、反馈是否友好。(6) **文档质量** - 文档是否完善、是否有开发者指南。
</details>

## 七、Java开发者提示

> 帮助有Java背景的开发者参与AI开源项目

| 开源贡献概念 | Java类比 | 说明 |
|------------|---------|------|
| GitHub Fork | Git Fork(通用) | Fork操作完全相同 |
| pip install -e . | mvn install / gradle build | 开发模式安装 |
| pytest | JUnit | 测试框架类比 |
| pre-commit hooks | Git hooks / Checkstyle | 提交前自动检查 |
| black/isort | Google Java Format | 代码格式化工具 |
| flake8 | Checkstyle / PMD | 代码规范检查 |
| mypy | Java编译器类型检查 | Python的类型检查器 |
| PR (Pull Request) | PR (通用) | 代码审查流程相同 |
| Code Review | Code Review (通用) | 代码审查文化相同 |
| GitHub Actions CI | Jenkins CI | CI/CD工具类比 |
| Issue Tracker | JIRA / GitHub Issues | 问题追踪类比 |
| CONTRIBUTING.md | CONTRIBUTING.md(通用) | 贡献指南 |
| Semantic Versioning | Semantic Versioning(通用) | 版本管理规范相同 |

### 关键思维转换

1. **Python项目结构更灵活**: 没有Maven那样严格的目录约定，但大多数项目遵循类似的模式（src/tests/docs）
2. **测试驱动贡献**: 开源项目非常重视测试覆盖，先写测试再写代码是常态
3. **文档也是贡献**: 在AI开源项目中，文档改进是被高度重视的贡献类型
4. **社区沟通很重要**: 技术只是贡献的一部分，良好的沟通能力同样重要
5. **从小处开始**: Java开发者往往习惯"大而全"，在开源中应从小的改进开始，逐步建立信任
